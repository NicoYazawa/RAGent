一、RAG 技术概述

1.1 什么是检索增强生成

检索增强生成（Retrieval-Augmented Generation，RAG）是一种将信息检索与大语言模型生成相结合的技术架构。其核心思想是：在大模型回答用户问题之前，先从外部知识库中检索出与问题相关的文档片段，将检索结果作为上下文注入提示词，让模型基于真实资料作答，从而有效缓解大模型知识过时、私有领域知识缺失与幻觉三类问题。

1.2 与纯大模型问答的对比

一、知识时效性：纯大模型的知识截止于训练时间点，RAG 可实时接入增量文档；
二、私有知识：大模型没有企业内部文档知识，RAG 将私有知识外置为可检索索引；
三、可溯源性：大模型直接生成的内容无法验证出处，RAG 每个回答都能定位到具体文档切片；
四、成本控制：相比微调模型，RAG 无需重新训练，更新知识只需重建索引，边际成本低。

1.3 RAGent 的演进

传统 RAG 是一条固定流水线：检索 → 拼接 → 生成。RAGent（智能体化 RAG）引入决策智能体，由智能体动态决定「是否检索、检索什么、检索几次、是否需要补全、答案是否合格」，将流水线升级为可自我纠正的闭环系统。本系统即为 RAGent 架构的完整实现。

二、知识入库流水线

2.1 文档解析

系统支持四种文档格式的解析：

一、Markdown（.md）：按 # 标题层级维护路径栈，产出形如「一级标题/二级标题/三级标题」的章节路径；
二、纯文本（.txt）：按中文章节标题正则（如「第一章」「一、」「1.2.3」）识别层级切分；
三、PDF（.pdf）：逐页提取文本，页内再按章节正则切分；
四、Word（.docx）：按段落样式（Heading 样式）与标题正则双通道识别结构。

2.2 语义切片

切片（Chunking）是 RAG 效果的关键环节。切片过大导致检索粒度粗糙、噪声多；切片过小导致语义割裂、上下文不足。本系统采用「结构感知切片」策略：

一、默认参数：目标切片 500 token，相邻切片重叠 50 token；
二、结构优先：以解析阶段产出的章节块为基本单元，小节合并，大节切分，切片携带完整章节路径；
三、切片元数据：每个切片记录 doc_id、chunk_uid、chunk_no、section_path、content 与 token_count，全部持久化到 MySQL 与 Elasticsearch。

2.3 向量化

切片文本通过嵌入模型（默认 text-embedding-v4，输出 1024 维稠密向量）转化为语义向量。批量向量化按每批 10 条并行请求，支持失败重试。向量与原文共同写入 Elasticsearch 的 dense_vector 字段，构建 HNSW 近似最近邻索引（m=16，ef_construction=128）。

2.4 状态机

文档入库遵循严格状态机：parsing（解析）→ chunking（切片）→ embedding（向量化）→ ready（就绪）。任一阶段失败进入 failed 状态并记录错误详情，支持从失败点一键重试；重试前自动清理旧切片与旧索引，保证幂等。

三、混合检索与融合

3.1 双路召回

一、向量检索：将用户问题编码为向量，在 ES 中执行 kNN 搜索，召回语义相近的切片（Top 5）；
二、关键词检索（BM25）：对问题做分词后执行全文检索，召回字面精确匹配的切片（Top 5），弥补向量检索对专有名词、编号、缩写的不足。

3.2 RRF 倒数排序融合

两路结果通过 Reciprocal Rank Fusion 合并。RRF 公式为：score(d) = Σ 1/(K + rank_i(d))，其中 K 取 60，rank_i(d) 为文档 d 在第 i 路检索中的名次。RRF 无需调权、对分数量纲不敏感，是多路检索融合的稳健方案。融合后取 Top 8 进入相关性评估。

3.3 相关性评估与 CRAG

评估器对每条候选切片独立打分（1-10 分）：

一、score ≥ 7：correct，直接作为引用上下文；
二、5 ≤ score < 7：partial，触发 CRAG（Corrective RAG）流程——剥离无关句、保留核心句，并触发一次查询改写后的补充检索；
三、score < 5：incorrect，直接丢弃。

若全部候选为 incorrect，智能体判定「知识库无法回答」，明确告知用户而不是强行编造。

四、智能体决策与反思

4.1 意图识别

智能体首先对用户输入分类：知识问答 / 数据查询 / 网络搜索 / 闲聊。分类同时完成指代消解，将「它支持哪些格式」补全为「智答支持哪些文档格式」。

4.2 数据源路由

按意图选择通路：知识问答路由到混合检索；数据查询路由到 NL2SQL 链路；实时性问题（如「今天」「最新」）路由到网络搜索；闲聊直接生成。多条通路可组合，例如「对比我们产品与竞品最新售价」同时触发知识库检索与网络搜索。

4.3 反思重答

答案生成后进入自检：是否引用了检索内容？是否完整回答了问题？是否包含矛盾表述？自检不通过则触发反思，智能体重新规划检索词或调整回答结构，最多重试 2 轮，仍不通过则以最佳候选答案输出并附带低置信提示。

4.4 决策日志

六个决策点（意图识别、数据源选择、检索评估、知识补全、反思重答、引用组装）的输入、输出、耗时与置信度全量落库，前端以流程图与时间线形式可视化，便于调试与效果归因。

五、NL2SQL 数据问答

5.1 生成与校验

智能体依据预先注入的表结构 Schema（表名、字段、枚举值、样例数据）生成 SQL。执行前经过三层校验：

一、语法校验：SQL 解析器语法检查；
二、安全校验：白名单只允许 SELECT，正则黑名单拦截 DROP / DELETE / UPDATE / INSERT / TRUNCATE / ALTER；
三、成本校验：EXPLAIN 预估扫描行数，超过 100 万行的查询强制加 LIMIT 或拒绝执行。

5.2 证据链

数据问答回答附带三重证据：生成的 SQL 语句、执行结果表格（最多展示 50 行）、命中字段的数据来源说明，用户可点击验证每个数字的来源。

六、工程性能优化

一、流式输出：回答全程 SSE 流式推送，决策事件、检索过程、正文逐段到达前端，首字节时间低于 2.5 秒；
二、超时熔断：单轮问答总超时 120 秒，检索、生成子阶段分级超时；
三、历史压缩：多轮对话保留最近 8 轮上下文，超出部分摘要压缩；
四、缓存策略：相同问题的检索结果按 embedding 相似度缓存，命中阈值 0.98，缓存命中时检索耗时降至 50 毫秒以内。

七、评测体系

7.1 评测指标

一、检索质量：Recall@5、MRR（平均倒数排名）、NDCG@10；
二、生成质量：答案准确率（人工标注）、引用命中率（引用是否真实支撑答案）、幻觉率；
三、系统性能：检索 P95 延迟、端到端 P95 延迟、吞吐量 QPS。

7.2 评测集建设

内部标准评测集覆盖 1200 个问题，按问题类型分为事实型（40%）、对比型（20%）、计算型（15%）、列表型（15%）、否定型（10%，考察「知识库没有时承认不知道」）。每次版本迭代全量回归，指标劣化超过 1 个百分点阻塞发布。

八、参考实现组件

一、后端框架：FastAPI + uvicorn，SSE 由 sse-starlette 提供；
二、编排与模型接入：LangChain 风格的链式编排，OpenAI 兼容协议接入 DeepSeek 与百炼嵌入；
三、存储：MySQL 8.x（业务元数据）+ Elasticsearch 8.x/9.x（全文、向量与日志）；
四、前端：Vue 3 + TypeScript + Vite，流程可视化基于 SSE 决策事件流驱动。
