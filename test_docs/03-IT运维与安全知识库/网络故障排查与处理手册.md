# 网络故障排查与处理手册

> 文档编号：OPS-NET-2026-003 ｜ 版本：V2.6 ｜ 更新日期：2026-05-12 ｜ 适用角色：网络工程师、值班运维

## 一、排查总体方法论

### 1.1 分层排查模型

网络故障排查遵循自底向上的分层定位法，按顺序排查，避免跳层猜测：

1. **物理层**：线缆、光模块、端口状态（up/down）、CRC 错包；
2. **链路层**：VLAN 划分、生成树阻塞、链路聚合状态、MAC 地址表；
3. **网络层**：路由收敛、ARP 表、ICMP 连通性、TTL 异常、MTU 分片；
4. **传输层**：端口监听、连接状态（SYN_SENT / CLOSE_WAIT 堆积）、防火墙策略；
5. **应用层**：DNS 解析、证书校验、负载均衡健康检查、应用超时配置。

### 1.2 黄金四问

接到故障报告后，值班工程师必须先确认四个问题再动手：

- 故障范围：单机、单机房还是全网？（决定影响面定级）
- 时间特征：持续存在还是间歇出现？何时开始？
- 变更关联：故障时间点前后是否有网络/系统变更？
- 复现条件：能否稳定复现，依赖什么路径与协议？

## 二、常用排查命令速查

### 2.1 连通性定位

| 目的 | 命令 | 关注点 |
| --- | --- | --- |
| 链路连通 | `ping -c 100 <target>` | 丢包率、RTT 抖动（单次 ping 无意义） |
| 路径追踪 | `traceroute -T -p 443 <target>` | 在哪一跳开始异常、是否绕路 |
| 端口可达 | `telnet <ip> <port>` / `Test-NetConnection` | TCP 是否可建立 |
| 本地路由 | `ip route get <dst>` | 出接口与下一跳是否符合预期 |
| ARP 状态 | `arp -n` | ARP 是否为真实网关 MAC（防 ARP 欺骗） |

### 2.2 服务器侧网络栈检查

- `ss -s`：连接总数概览，TIME_WAIT/CLOSE_WAIT 是否异常堆积；
- `ss -tan state close-wait`：定位 CLOSE_WAIT 对应进程（通常是应用未调用 close）；
- `dmesg -T | grep -i nic`：网卡驱动报错、链路抖动记录；
- `ethtool -S eth0 | grep -iE 'err|drop|discard'`：网卡级丢包与 CRC 错误计数；
- `conntrack -S`：连接跟踪表是否打满（满表会导致新建连接随机失败）。

## 三、典型故障处理预案

### 3.1 案例 A：单台服务器无法访问外网

**现象**：应用报连接超时，其他机器正常。

**排查路径**：

1. `ping 网关`：不通则检查本机 IP/掩码/网关配置与交换机端口 VLAN；
2. 网关通但 `ping 8.8.8.8` 不通：核对默认路由与防火墙出网白名单；
3. IP 通但域名不通：`nslookup` 检查 DNS，切换 223.5.5.5 对比验证；
4. 均正常但业务端口不通：检查 iptables/nftables 规则与云安全组。

**常见根因统计**（近 12 个月）：安全组未放行 38%、DNS 配置错误 27%、路由缺失 18%、本机防火墙 12%、其他 5%。

### 3.2 案例 B：负载均衡健康检查批量失败

**现象**：SLB 摘除多台后端，服务容量骤降。

**处理步骤**：

1. 立即查看后端机负载：CPU 打满（如 95%+）导致健康检查响应超时，先扩容再排查；
2. 后端正常则检查健康检查探测路径：`curl -v http://127.0.0.1/healthz`，确认本地可达；
3. 本地可达但 SLB 不通：核对安全组是否放行 SLB 探测网段；
4. 确认健康检查阈值配置：连续失败次数（建议 3 次）与间隔（建议 2 秒）是否被误改；
5. 恢复后将阈值改回并检查配置审计日志，定位误操作来源。

### 3.3 案例 C：跨机房专线丢包

**现象**：专线链路丢包 3%，数据库主从延迟告警。

**处理要点**：

1. 两端交换机对同一条链路执行 `display transceiver` 与光功率检查：收发光功率是否在阈值内；
2. 逐段打流测试（iperf3 -P 8），定位丢包发生在运营商段还是机房内段；
3. 若为运营商侧劣化：立即切换备用专线（BGP 自动切换失败时手动切换），并提交运营商工单要求 4 小时内反馈；
4. 切换后观察 30 分钟主从延迟追平（Seconds_Behind_Master 归零）再关闭事件。

### 3.4 案例 D：DNS 解析间歇失败

**现象**：偶发「域名无法解析」，重试成功。

**排查方向**：

1. 客户端侧：`nslookup <domain> <dns_ip>` 分别指定主备 DNS 对比失败率；
2. DNS 服务侧：检查 dnsmasq/coredns 负载与上游转发超时配置（建议 forward_timeout 2s）；
3. 检查解析记录 TTL：过短 TTL（低于 30s）在 DNS 抖动时放大失败概率；
4. 应急措施：核心域名在应用侧配置本地 hosts 兜底或启用 DNS 缓存（systemd-resolved / nscd）。

## 四、告警分级与响应要求

| 级别 | 定义 | 示例 | 响应/升级时限 |
| --- | --- | --- | --- |
| P1 | 全网或核心业务中断 | 机房级断网、核心交换机宕机 | 5 分钟响应，30 分钟内升级 CTO |
| P2 | 部分业务受损 | 单专线丢包、SLB 异常摘除 | 15 分钟响应，2 小时未恢复升级 |
| P3 | 无即时影响但存在风险 | 冗余链路单条 down、丢包 0.5% | 当班内处理，24 小时闭环 |
| P4 | 观察类 | 光功率临界、错误包缓慢增长 | 建跟踪工单，周内评审 |

## 五、工具与权限管理

- 网络设备配置修改必须通过堡垒机，保留完整会话录像；
- 生产网络设备只允许运维组与网络组成员登录，账号每季度审计一次；
- 抓包排障（tcpdump）只允许在目标服务器执行，抓包文件可能包含敏感数据，分析完毕 48 小时内删除；
- 每次故障处置后 3 个工作日内补充/更新本手册案例库，由网络组周会评审合入。
