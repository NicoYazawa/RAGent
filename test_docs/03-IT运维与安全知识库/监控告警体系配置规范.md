# 监控告警体系配置规范

> 文档编号：OPS-MON-2026-004 ｜ 版本：V2.2 ｜ 更新日期：2026-06-01 ｜ 适用范围：全量生产服务、中间件、数据库与网络设备

## 一、监控分层架构

### 1.1 指标采集分层

监控体系按四层采集，所有指标统一汇入 Prometheus 集群（2 副本高可用），告警经 Alertmanager 分发：

| 层级 | 采集方式 | 抓取间隔 | 典型指标 |
| --- | --- | --- | --- |
| 基础设施层 | node_exporter | 15s | CPU、内存、磁盘、网络 |
| 中间件层 | 各类 exporter | 15-30s | MySQL/Redis/Kafka/ES 指标 |
| 应用层 | 应用内置 /metrics | 30s | QPS、错误率、P99 延迟、GC |
| 业务层 | 自定义上报 | 60s | 订单量、支付成功率、问答准确率 |

### 1.2 指标命名规范

- 格式：`<域>_<对象>_<指标>_<单位>`，如 `app_chat_first_token_ms_p95`；
- 禁止使用无语义命名（如 metric1）；新增指标必须登记《指标字典》；
- Label 规范：必须携带 `env`（prod/pre）、`cluster`、`instance`；禁止在 label 中使用用户 ID 等高基数值。

## 二、核心告警规则

### 2.1 基础资源告警

| 规则 | 表达式（示意） | 持续时间 | 级别 |
| --- | --- | --- | --- |
| CPU 使用率过高 | node_cpu_util > 0.90 | 10m | P3 |
| 内存使用率过高 | mem_util > 0.92 | 5m | P3 |
| 磁盘空间不足 | disk_free_pct < 0.10 | 5m | P2 |
| 磁盘预测耗尽 | 预测 48h 内写满 | - | P2 |
| 节点不可达 | up == 0 | 1m | P2（核心节点 P1） |

### 2.2 应用服务告警

1. **可用性**：健康检查失败或 Pod 重启超过 3 次 → P2；核心服务（对话、检索）不可用 → P1；
2. **错误率**：HTTP 5xx 比例超过 1% 持续 5 分钟 → P3；超过 5% → P2；
3. **延迟**：对话接口首 token P95 超过 4 秒持续 10 分钟 → P3；
4. **饱和度**：工作队列积压超过 1000 或消费者 lag 超过 50000 持续 15 分钟 → P3。

### 2.3 数据库与中间件告警

- MySQL 主从延迟大于 60 秒 → P2；连接数使用率超过 85% → P3；
- Redis 内存使用率超过 90% 或主从断连 → P2；
- Kafka 消费组 rebalance 频繁（每小时超过 3 次）→ P3；
- ES 集群状态 yellow 超过 30 分钟 → P3，red → P1；分片未分配 → P2。

## 三、告警分级与值班路由

### 3.1 分级标准

- **P1（灾难）**：核心业务全面不可用，需立即电话叫醒多人响应；
- **P2（严重）**：业务明显受损或冗余尽失，值班工程师立即处理；
- **P3（警告）**：存在劣化趋势，当班处理；
- **P4（提示）**：仅 IM 群通知，进工单跟踪。

### 3.2 通知路由矩阵

| 级别 | 通知渠道 | 响应要求 |
| --- | --- | --- |
| P1 | 电话（值班+经理+负责人） + IM 应急群 | 5 分钟内响应 |
| P2 | 电话（值班） + IM 值班群 | 15 分钟内响应 |
| P3 | IM 值班群 + 工单 | 2 小时内跟进 |
| P4 | 工单自动创建 | 按排期处理 |

静默规则：同一告警组 15 分钟内只通知一次；维护窗口（变更单审批通过）自动静默；禁止手工 silence 超过 24 小时，超时须值班经理审批。

### 3.3 升级机制

P1 告警 30 分钟未确认自动升级通知 CTO；P2 告警 2 小时未恢复升级为值班经理跟进；升级事件必须在事后复盘中说明响应超时原因。

## 四、告警质量治理

### 4.1 噪音控制目标

- 周告警总量环比波动超过 30% 需要专项分析；
- 告警有效率（触发后确需人工处理的占比）目标不低于 70%；
- 月度告警复盘会输出规则优化清单：合并重复规则、收紧持续时间、降级低价值告警。

### 4.2 新增告警规则流程

1. 提交人填写《告警规则申请单》：指标、阈值、级别、理由、预期频率；
2. 运维组周会评审（重点评估是否会变成噪音源）；
3. 先以 P4 观察 7 天，确认触发频率合理后调整到正式级别；
4. 规则入库统一 Git 管理，任何修改必须走 MR 评审，禁止在页面上直接改规则。

## 五、值班与闭环

- 值班表每月 25 日前排定下月，主值/副值轮换，交接班须同步未闭环告警；
- 所有 P1/P2 告警必须关联事件单，处置过程记录时间线，恢复后 3 个工作日内完成复盘；
- 复盘产出四要素：时间线、根因、改进项（落实到人）、验证方式；改进项完成率纳入运维组季度考核，目标 90% 以上。
